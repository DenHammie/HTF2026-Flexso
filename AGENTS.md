# AGENTS.md — Oakhaven (HTF 2026)

Guide for AI coding assistants working in this repository. Read it before changing anything.

## What this is

A small **SAP CAP + SAPUI5 (TypeScript)** project for a student hackathon. The repo holds the data
of a fictional village ("Oakhaven"), two read-only OData services on top of it, and one UI5 app that
shows the raw data. The team builds its own features on top of it. There is no real SAP system,
no cloud deployment and no external API — everything runs locally in Docker on SQLite.

The human you work with is new to CAP and UI5: explain what you change and why, keep changes small
and runnable, and prefer the standard, documented way of doing things over clever shortcuts.

## Where the requirements come from

The team builds for four villagers (Maren the water keeper, Tobin the baker, Rowan of the village
council, Ilse the librarian). **Their requirements are not in this repo.** The team gathers them by
interviewing the villagers in a chat on the HTF platform, with a limited number of questions.

- **Never invent requirements, thresholds, priorities or rules.** If the team asks "what should we
  build?" or "when is a pipe broken?", say that only the villager knows, and help them phrase a
  sharp, specific question for the chat instead.
- When the team pastes what a villager said, help them turn it into a plan and code, and point out
  what is still unclear so they can ask a follow-up.
- Judging is on the solution, not the code: help them build something the villager can use, and
  help them explain their choices.

## Commands

Everything runs in Docker. From the host, prefix commands with `docker compose exec app` while the
stack runs; inside the VS Code Dev Container terminal run them as-is.

| Command | Purpose |
| --- | --- |
| `docker compose up --build --watch` | start (first time / after dependency or new-app changes) |
| `docker compose up --watch` | start (later) |
| `docker compose exec app npm run db:reset` | recreate the SQLite DB from schema + CSVs |
| `docker compose exec app npm run typecheck` | `tsc --noEmit` over everything |
| `docker compose exec app npm run lint:ui5` | UI5 linter for every app under `src/` |
| `docker compose exec app npm run build` | `cds build` (model compiles?) |
| `docker compose logs -f app` | server log |

**Done means:** `npm run typecheck` and `npm run lint:ui5` are clean, `cds build` succeeds, and the
change works in the browser at <http://localhost:4004/launchpad/index.html>.

## Conventions

### General

- **TypeScript only** for new code — backend handlers and UI5 code. Never add `.js` files.
- No `any`: use `unknown` + narrowing, or describe the shape with an `interface`. Explicit return
  types on exported functions. `const` by default, `===`, `async/await`.
- Keep the existing structure: services in `srv/`, helpers in `srv/lib/`, one folder per UI5 app in `src/`.
- Keep comments short and useful; keep the `👋 EXAMPLE` comments intact — they are teaching material.

### CAP — data model (`db/`)

- Entities use the aspects `cuid` (UUID key `ID`) and `managed` (`createdAt/By`, `modifiedAt/By`).
  Never declare those fields by hand; CAP fills them in on every CQL write.
- `Composition of many` for children that live and die with the parent, `Association to` for references.
  Foreign keys appear as `<name>_ID` (e.g. `pipe_ID`) in CSVs and OData.
- Quantities and measurements are `Decimal(p, s)`, never `Double`. Fixed value lists → CDS `enum` types.
- CSV files are named `oakhaven.curse-<Entity>.csv`; the header row uses element names. After
  changing the schema or a CSV, run `npm run db:reset`.

### CAP — services (`srv/`)

- A service `.cds` file exposes projections: `entity X as projection on db.X;`. Every exposed entity
  is `@readonly` — changes go through **actions** with a TypeScript handler.
- Each service has `@(path: '…', impl: 'srv/<file>')` — the `impl` (without `.ts`) is how CAP finds
  the TypeScript handler. Keep it when you add services.
- Handlers live in a class that extends `cds.ApplicationService`; register them in `init()` and end
  with `return super.init()`:
  - `this.before(event, entity, h)` → validate/default, `this.on(...)` → implement (actions),
    `this.after('READ', entity, h)` → enrich results (computed fields).
- `@sap/cds` has **no TypeScript declarations installed** in this project. The pattern used in every
  file:

  ```ts
  interface CdsService { init(): Promise<void>; after(event: string, entity: string, handler: (results: unknown) => unknown): void; }
  interface CdsApi { readonly ApplicationService: new (...args: readonly never[]) => CdsService; /* …only what you use */ }
  // eslint-disable-next-line @typescript-eslint/no-require-imports
  const cds = require('@sap/cds') as CdsApi;
  export default class MyService extends cds.ApplicationService { override async init(): Promise<void> { /* … */ return super.init(); } }
  ```

  Extend the local interfaces with exactly the members you use (e.g. `ql.SELECT`, `ql.UPDATE`,
  `log`). Do not switch to `import cds from '@sap/cds'` — there are no types to import.
- Query with CQL (`SELECT.from(...)`, `UPDATE(...).with(...)`, `INSERT.into(...)` from `cds.ql`), never
  string-built SQL. Select only the columns you need; never query inside a loop (use `{ in: [...] }`).
- Computed fields: `virtual null as myField : Type` in the service projection + an `after('READ')`
  handler. UI5 sends `$select` with only the bound fields, so the handler must read missing inputs
  from the DB (one query, by `ID`). The worked example in `srv/water-supply-service.ts` shows how.
- Bound actions: declare in `actions { … }` of the projection, implement with
  `this.on('<action>', '<Entity>', handler)`; inside, `req.data` holds the parameters and
  `req.subject` references the bound instance (`UPDATE(req.subject).with({...})`).
- Errors: `req.error(<4xx>, 'message', '<target field>')` for validation; never throw a bare `Error`.
- Logging: `cds.log('<module>')`, not `console.log`.
- No `@requires` / authentication: the app is open by design (local hackathon).

### UI5 (`src/`)

- Follow <https://sap.github.io/ui5-typescript/>. **Every UI5 class needs a `@namespace` JSDoc tag**
  matching its location, or the module silently fails to load (white screen, no error):
  `/** @namespace oakhaven.village.controller */` for controllers, `oakhaven.village` for `Component.ts`,
  `oakhaven.village.model` for helper modules, etc.
- Import UI5 modules ES-style (`import JSONModel from "sap/ui/model/json/JSONModel";`), never via
  globals (`sap.m.Button`, `sap.ui.getCore()`). Type events with the generated types
  (e.g. `Button$PressEvent` from `sap/m/Button`).
- `manifest.json` is the source of truth: data sources, models, libraries, routing, launchpad inbound.
  Declare every library you use under `sap.ui5.dependencies.libs` **and** in `ui5.yaml`.
- XML views only; give every control a stable `id`. Event handlers are dot-prefixed (`press=".onSave"`);
  other modules (formatters, types) are pulled in with `core:require`.
- Bind, don't push: bind aggregations (`items="{/WaterPipes}"`) with a template; filter and sort via
  the binding (`sap/ui/model/Filter`, `Sorter`). Use the **OData V4 model** (`bindList`, `bindContext`,
  `requestObject`, operation bindings + `invoke()` for actions). A `JSONModel` is for view state only.
- The default model talks to WaterSupplyService; the `food` model to FoodStockService
  (`{food>name}`, `items="{food>/StockItems}"`).
- In a controller, reach the OData model via `this.getOwnerComponent()?.getModel()` (the view's model
  may not be set yet in `onInit`).
- **All user-facing text in `i18n/i18n.properties`** (`{i18n>key}`); placeholders `{0}` instead of
  string concatenation.
- Resources inside the app (images, JSON) are addressed with `sap.ui.require.toUrl("oakhaven/village/…")`,
  so they also work inside the launchpad.
- Use `sap/base/Log` for your own logging.
- Clean up in `onExit`: destroy dialogs/fragments you created, clear intervals.
- Custom CSS goes in `webapp/css/style.css` and uses theme parameters (`var(--sapPositiveColor)`,
  `var(--sapContent_LabelColor)`, …) — never style a control's internal DOM, never inline styles in XML.

### Fiori / UX

- Theme **`sap_horizon_dark`**; apps set `sap.ui.fullWidth: true`. Start from `sap.f.DynamicPage`;
  use `sap.f.FlexibleColumnLayout` for list → detail.
- Show **status as text + icon + semantic colour together** — e.g. `sap.m.ObjectStatus` with
  `state="Success|Warning|Error|Information|None"` and an icon. Never colour alone (accessibility).
  Use the semantic states, not hex colours.
- Numbers with units: `sap.m.ObjectNumber` (`number` + `unit`). Dates: an OData type with
  `formatOptions` (see `Main.view.xml`), never hand-formatted strings.
- Empty states: `sap.m.IllustratedMessage` or `noDataText`; busy states on the control (`busy`),
  remember `busy=false` on error paths. Errors: `MessageBox.error` with the server's message;
  `MessageToast` only for success.
- One primary (`Emphasized`) action per area; icon-only buttons need a `tooltip`.

### Launchpad

- Every folder under `src/` with a `ui5.yaml` + `webapp/manifest.json` gets a launchpad tile —
  generated from `sap.app.crossNavigation.inbounds` (semanticObject + action + title/subTitle/icon,
  texts from the app's i18n). No change in `launchpad/` is ever needed.
- A new app needs a unique `sap.app.id`, `metadata.name`, `mountPath` (e.g. `/app/<name>`) and
  `semanticObject`. App URLs never contain `/webapp`.

## How to add things (short)

- **Field:** `db/schema.cds` → (CSV column) → `npm run db:reset` → bind it in a view.
- **Computed field:** copy the `👋 EXAMPLE` pattern (virtual element + `after('READ')` + column).
- **Action that writes:** `actions { action x(...) returns ...; }` on the projection →
  `this.on('x', 'Entity', handler)` → call it from UI5 with
  `model.bindContext("<Service>.x(...)", context)` + `setParameter` + `invoke()`.
- **New app:** copy `src/oakhaven-app`, rename id/namespace/mountPath/semanticObject everywhere,
  `docker compose up --build --watch`. Full recipes: README → *Recipes*.

## Gotchas

- **Windows / OneDrive:** file-change events do not reach the container. Always start with
  `docker compose up --watch` — Docker's own watcher restarts the server for `srv/`, `db/`,
  `.cdsrc.json` and rebuilds on `package.json`.
- **UI5 changes** (`src/**`) need no restart — refresh the browser (hard refresh `Ctrl+Shift+R`
  when in doubt).
- **CSV or schema changes** need `npm run db:reset`; the live DB is `db/oakhaven.sqlite` (git-ignored).
- **New app or new UI5 library** → `docker compose up --build --watch` (the image pre-downloads the
  UI5 libraries listed in each `ui5.yaml`).
- The first request after a start is slow (TypeScript is compiled on demand).
- `srv/lib/demo-freshness.ts` updates `Sensors.lastReading` every 20 s while the server runs — that
  is expected, not a bug.
- A launchpad console 404 for `homepage-af-dep.js` is harmless.
- `cds build --production` would copy `.ts` handlers as-is; there is no production deployment here,
  so this does not matter.
